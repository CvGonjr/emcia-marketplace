    feat(nucleo+campo): require case seal after P2 to open/close P3b
    
    Replaces the standalone contraste execution (decisions 014-020,
    separate plugin/repo eiac-contraste running the full method
    independently) with an in-case comparison: the declared state, sealed
    at the end of P2, versus the verified state that P3b/P3d produce from
    the in-person field walk. Registered as decision 021, superseding 004
    and 014-020 (019's general componente-authorship rule stays firm; only
    its contraste-specific part is superseded).
    
    The gate is declarative, not hard-coded: the playbook marks P3b with
    {"exige_selo_apos": "P2"} (playbook v0.4.1 -> v0.4.2); the nucleus
    never names "P2" or "P3b" in code. New estado.eventos() reads the full
    trail; new playbook.selo_apos_etapa() compares EtapaEncerrada/
    SeloAplicado by their POSITION in that trail, not by timestamp -- two
    events can land in the same second (estado.evento() uses second
    precision), and a fast percurso (including the test suite itself)
    produced a false negative when compared by data. Position is the
    reliable ordinator. Wired into guarda.py (new G7, blocks opening) and
    avancar.py::encerrar() (blocks closing).
    
    The contraste isolation guard in guarda.py/selar.py is left in place
    per explicit instruction -- it doesn't conflict with the new gate, but
    now protects against an execution path that's no longer part of the
    project; flagged in resultado.md as a candidate for future removal.
    
    New testes/verificacao_por_estados.py (7 checks, negatives first: no
    seal, seal before P2's closure, then the positive control). Fixed
    regression this gate caused in four pre-existing suites that build
    F0->P3b percursos without sealing after P2 (nucleo_2_6_1.py,
    campo_2_6_3.py, campo_2_6_5.py, campo_2_6_6.py) -- none of their
    assertions changed meaning, only the command sequence that reaches the
    state they check.
